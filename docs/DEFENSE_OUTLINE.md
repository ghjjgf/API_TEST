# API_TEST 系统答辩汇报大纲架构

## 一、汇报定位

- 汇报主题：**从接口验证到统一测试平台：API_TEST 功能、业务与性能测试体系建设**
- 汇报时长：建议 18-20 分钟，问答 5-10 分钟
- 建议页数：核心 20 页 + 附录 5 页
- 叙事主线：背景痛点 → 建设目标 → 系统架构 → 子系统能力 → 实测结果 → 问题洞察 → 价值与展望
- 核心观点：本项目不是单一脚本集合，而是一套覆盖功能、业务流程、性能压测和统一报告的持续测试资产。

## 三、核心页架构

### 第 1 页：封面

- 标题：API_TEST 接口功能、业务与性能测试系统
- 副标题：从接口验证到统一测试平台的建设与实践
- 信息：汇报人、导师/评委、日期
- 视觉：系统总架构缩略图或“Function / Business / Performance / Report”四象限
- 讲稿重点：一句话说明项目横跨 7 月 29 日至今，形成完整测试闭环。

### 第 2 页：一页结论与汇报目录

- 一页结论：建成统一入口、统一数据、统一断言、统一报告的 API 测试平台。
- 三项成果：
  - 9 类功能接口、219 条可执行功能用例
  - 15 个业务场景、164 个业务验证步骤
  - 5 类性能测试入口，覆盖 Search、Entity、Detect
- 目录：背景与目标、系统架构、测试实施、结果分析、问题反思、未来规划
- 讲稿重点：先给评委完整结论，再逐层展开。

### 第 3 页：背景与痛点

- 原始问题：
  - 接口数量多，Repo、Entity、Search、Detect 调用方式不一致
  - 手工测试难复用、难复现、结果分散
  - 功能测试与业务链路脱节
  - 性能测试缺少统一数据、统一指标和统一报告
  - 参数校验、状态码、异常行为缺少系统化覆盖
- 视觉：问题鱼骨图或“测试前”场景流程
- 讲稿重点：项目源于真实接口质量验证需求，而非单纯开发测试脚本。

### 第 4 页：建设目标与范围

- 四个目标：
  - 可执行：统一入口运行功能、业务和性能测试
  - 可验证：状态码、响应体、业务结果和性能指标均可断言
  - 可追溯：输入用例、原始响应、汇总结果和报告完整归档
  - 可扩展：按模块、接口、场景和并发梯度扩展
- 覆盖范围：Repo、Entity、Search、Detect
- 边界：Repo Update、Entity Update 当前为设计用例，尚未形成完整执行闭环
- 讲稿重点：目标不是“跑一次测试”，而是构建持续可用的测试能力。

### 第 5 页：7 月 29 日至今工作演进时间线

- 阶段一：需求梳理、接口摸底、测试方案设计
- 阶段二：功能测试框架与参数校验体系
- 阶段三：业务链路场景扩展
- 阶段四：性能测试框架、k6 编排和指标统计
- 阶段五：Search 热点库、统一报告和问题复盘
- 视觉：横向时间线，每阶段配一个关键产物
- 讲稿重点：强调从单点验证逐步演进为平台化体系。

### 第 6 页：系统总体架构

```text
main.py 统一入口
  ├─ function_test → api → core → 服务端
  ├─ business      → api → core → 服务端
  └─ performance   → k6/Python → performance/outputs
                         ↓
                    outputs/report.html
```

- 核心层：入口层、适配层、核心能力层、测试层、数据层、报告层
- 讲稿重点：统一入口和统一底层能力是系统可维护性的基础。

### 第 7 页：接口适配与核心能力层

- `api/`：RepoApi、EntityApi、SearchApi、DetectApi
- `core/`：aiohttp 异步客户端、响应模型、结果收集、响应归档、轮询
- `config/`：比对服务、检测服务、端口和超时配置
- 特点：请求细节集中在适配层，避免测试用例重复拼接 HTTP
- 视觉：接口适配层类图与请求链路
- 讲稿重点：业务和功能测试都通过同一 API 适配层访问服务端。

### 第 8 页：功能测试子系统

- 9 类可执行接口：
  - Repo：create/get/list/delete
  - Entity：create/get/delete
  - Search：query
  - Detect：run
- 219 条可执行功能用例
- 用例类型：合法、非法、非空、缺失、类型错误、路径错误、方法错误
- 输出：pytest 结果、summary JSON、verdict JSON、响应归档
- 讲稿重点：功能测试负责最小接口动作和契约级验证。

### 第 9 页：业务场景测试子系统

- Repo：容量、复制、轮转、删除策略、预过滤、FeatureIDMap
- Entity：版本比较、仓库版本控制、实体重读
- Search：include 阈值、多数据、多仓库、版本类型校验
- Detect：高级字段、ROI、用户对象
- 共 15 个场景、164 个验证步骤
- 讲稿重点：业务测试验证跨接口组合行为，而非单接口返回。

### 第 10 页：性能测试子系统

- 5 类性能入口：
  - Search baseline + hotspot
  - Entity Insert
  - Entity Get
  - Entity Delete 闭环
  - Detect 多类型、图片/文件、单目标/多目标
- 技术方案：Python 编排 + k6 发压 + aiohttp 辅助 + Python 统计
- 指标：QPS、P50、P95、P99、平均/最大延迟、成功率、错误率、超时、连接错误
- 讲稿重点：性能测试同时关注吞吐、时延、稳定性和资源压力。

### 第 11 页：测试数据、断言与响应归档

- 输入：`data/` 和 `performance/data/`
- 断言：状态码、响应体结构、业务字段、内部 Detect 结果、性能阈值
- 归档：请求 payload、响应体、错误信息、耗时、证据文件
- Token 展开：参考特征、检测图片、动态资源 ID
- 讲稿重点：测试结果可追溯到具体输入和原始响应。

### 第 12 页：统一编排与 HTML 报告

- `main.py` 统一选择功能/性能接口
- 支持全量执行、单项执行、Collect Only 汇总
- 解析 summary、verdict、业务响应和性能 Markdown
- 自动生成功能、业务、性能三类报告和图表
- 当前报告包含 170 个表格、5 个主章节
- 讲稿重点：将分散结果自动汇总为可答辩、可交付的统一报告。

### 第 13 页：工作量与工程产出总览

- 508 个文件、79 个 Python 文件、约 1.7 万行 Python 代码
- 223 个 JSON 数据/结果文件
- 4 个 API 领域、9 类功能接口、15 个业务场景、5 类性能测试
- 3 份测试方案 PDF
- 输出 HTML、Markdown、JSON、PNG 四类成果
- 视觉：数字卡片 + 模块分布图
- 讲稿重点：展示从方案、代码、数据到报告的完整工作量。

### 第 14 页：功能测试结果与问题发现

- 最新原始结果：99/219 通过，120 条未通过
- 重点问题簇：
  - Repo 创建成功后普遍返回 202，测试预期为 201
  - 多类非法参数期望 400，实际返回 404/500
  - Entity Get/Delete 的历史预期与服务行为存在明显差异
  - Search 多类非法输入返回 200/500
  - Detect 高级字段结果存在误检和漏检
- 讲稿重点：这些失败体现测试价值，暴露接口契约、实现和文档之间的偏差。

### 第 15 页：业务测试结果与链路问题

- 最新业务结果：149/164 通过，约 90.85%
- 通过场景：高级字段、实体重读、删除、删除策略、include 阈值
- 失败场景：
  - PreFilter 位置和时间过滤不符合预期
  - Replications 更新与容量状态异常
  - Rotate 旧实体未被正确淘汰
  - 版本比较和版本控制未阻止错误版本
  - UseFeatureIDMap 当前不支持
  - 多库和多特征存在兼容限制
- 讲稿重点：业务场景揭示了单接口测试无法发现的问题。

### 第 16 页：Entity 性能测试结果

- Entity Get：最高约 15,259 QPS，P95 约 63 ms，错误率 0
- Entity Insert：最高约 8,244 QPS，P95 约 149 ms，错误率 0
- Entity Delete：约 146-345 QPS，P95 最高约 748 ms
- 结论：查询与插入表现优秀，删除链路吞吐明显偏低
- 视觉：QPS-并发折线图 + P95-并发折线图
- 讲稿重点：Entity 系统具备较高吞吐能力，删除是后续优化重点。

### 第 17 页：Detect 与 Search 性能结果

- Detect：
  - face-file 约 359 QPS，P95 约 134 ms
  - all-single-file 并发 32 时仅约 4.8 QPS，P95 约 18.7 秒
- Search：
  - 单库约 100-170 QPS
  - 1E + 5kw 双库约 55-66 QPS
  - 多 NPU 库仅约 7 QPS，P95 可达 15 秒
  - 完整运行曾因多库零成功请求而中止
- 讲稿重点：Search 多库和 Detect all 类型是主要性能风险。

### 第 18 页：工程亮点与项目价值

- 工程亮点：
  - 分层架构、统一入口、统一断言、统一报告
  - Python 与 k6 混合性能测试
  - Search baseline/hotspot 对比
  - 多环境安全阀、健康检查和零成功中止
  - 全量响应归档与问题追溯
- 项目价值：
  - 将手工验证转化为可重复测试资产
  - 用数据定位接口契约、业务逻辑和性能问题
  - 为后续回归测试和 CI 接入提供基础
- 讲稿重点：项目的核心价值是“发现问题并形成可持续验证能力”。

### 第 19 页：不足、风险与反思

- 功能预期与当前接口实现存在较大偏差，需重新校准测试基线
- 超大失败响应文件占用约 10.34 GB，存储治理不足
- Search 测试耗时较长，运行稳定性仍需提升
- `main.py` 过于集中，后续需拆分执行、解析、聚合和渲染
- 环境地址仍存在硬编码，`requirements.txt` 缺少 aiohttp/k6 说明
- Repo Update、Entity Update 尚未完成执行闭环
- 讲稿重点：主动说明不足，体现工程反思能力。

### 第 20 页：总结与后续规划

- 第一阶段成果：完成从 0 到 1 的统一 API 测试平台
- 第二阶段计划：
  - 修复或校准功能测试预期基线
  - 优化 Search 多库检索性能
  - 压缩失败数据并建立产物保留策略
  - 接入 CI 和回归门禁
  - 完成 Update 接口闭环
  - 建立性能基线和容量模型
- 结束语：继续从“能测试”走向“可持续、可量化、可回归”
- 讲稿重点：用清晰路线图收束答辩。

## 五、答辩主线金句

1. 项目从一个分散、难复现的接口验证需求出发，最终形成统一测试平台。
2. 功能测试解决“接口是否按契约工作”，业务测试解决“接口组合是否满足业务约束”，性能测试解决“系统能承受多大压力”。
3. 测试的核心价值不只是通过率，而是发现契约偏差、业务缺陷和性能瓶颈。
4. 已形成从测试设计、执行、取证、汇总到复盘的完整闭环。
5. 下一阶段目标是让测试平台从“可用”走向“稳定、自动、可回归”。

## 六、后续生成 PPT 时的页面原则

- 每页只表达一个核心结论
- 先讲结果，再讲实现
- 架构页采用模块图，流程页采用箭头图，结果页采用指标卡和折线图
- 问题页使用“现象 → 证据 → 根因 → 影响”结构
- 避免把大量日志和 JSON 直接搬入 PPT
- 功能失败统一归纳为问题簇，不在主页面逐条罗列 120 条失败
- 性能数据统一保留三位有效数字，并标注并发和测量窗口
- 讲稿按每页 45-70 秒设计，总时长控制在 18-20 分钟
